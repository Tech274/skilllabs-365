# Skilltrack 365 Labs — Production Runbook

Everything needed to deploy, verify, operate and recover the platform.

---

## 1. Frontend environment variables

Auto-generated by Lovable Cloud and inlined at build time (`.env`, never edit by hand):

| Variable | Purpose |
| --- | --- |
| `VITE_SUPABASE_URL` | Backend API URL |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Public anon key (safe in the browser) |
| `VITE_SUPABASE_PROJECT_ID` | Project ref, used for direct function URLs |

Never put a service-role key, Azure credential or Guacamole password in a `VITE_*` variable — those are browser-visible.

> **Note (Resource Providers):** Azure and AWS lab credentials are stored on
> `cloud_provider_accounts` (Admin → Resource Providers), not as ambient

> are historical; provision-lab resolves the active provider account at runtime.
>

## 3. Deploying database migrations

1. Migrations live in `supabase/migrations/` and are applied through the Lovable Cloud migration flow (approval required).
2. Never edit an applied migration; add a new one.
3. Every new `public` table needs `GRANT` + `ENABLE ROW LEVEL SECURITY` + policies in the same migration.
4. After a schema change, regenerate `src/integrations/supabase/types.ts` (auto-generated by the platform).

### Lab template lifecycle (canonical)

`draft` → `published` → `archived`

* `draft` — visible to admins/instructors only.
* `published` — the only status students can read (RLS: `status = 'published'`).
* `archived` — retained for history, hidden from students.

Enforced by the `lab_templates_status_check` constraint and the "Users can view published lab templates" policy. Do not introduce an `active` status again.

## 4. Deploying Edge Functions

Lovable-managed functions deploy automatically on save. Before shipping, run locally:

```bash
npm run functions:check   # deno check over every function
npm run functions:test    # deno test supabase/functions/
```

### Auth & CORS posture

* All functions deploy with `verify_jwt = false` and validate the token themselves via `supabase/functions/_shared/auth.ts` (`requireUser`, `requireRole`, `requireAdmin`, `requireOwnerOrAdmin`). This is required by the signing-keys system and keeps cron/service-role callers working.
* Service-role callers (cron) authenticate with `Authorization: Bearer <service role key>` — that key lives only in the scheduler configuration, never in the browser.
* CORS is origin-allowlisted (`corsHeadersFor`): `*.lovable.app`, `*.lovableproject.com`, `localhost`/`127.0.0.1`, plus anything in `ALLOWED_ORIGINS`. Wildcard `*` is never returned.

| Function | Caller | Guard |
| --- | --- | --- |
| `provision-lab` | student/instructor | JWT + Azure preflight + budget cap |
| `check-vm-status` | owner / admin | `requireUser` + `requireOwnerOrAdmin` |
| `guacamole-proxy` | owner / admin | JWT + VM ownership; scoped Guacamole token |
| `cleanup-idle-labs` | cron (service role), admin, **student `cancel-provisioning` only** | `requireAdmin`, or `requireUser` + `requireOwnerOrAdmin` for cancel |
| `cloud-access-session` | student | JWT + `user_can_access_template` |
| `cloud-provider-config`, `cloud-provider-health`, `azure-quota`, `daily-report`, `ai-health` | admin | `requireAdmin` |
| `ai-assistant`, `ai-chat` | signed-in user | `requireUser` + quota + circuit breaker |

## 5. Cleanup cron setup

`cleanup-idle-labs` handles, in one scheduled run (`action` omitted → `auto-cleanup`):

* idle VMs (no session activity > 15 min) → deallocate
* expired sessions (past `expires_at`) → deallocate / terminate
* VMs stuck in `provisioning` > 10 min → mark failed and delete the Azure resource
* orphaned Guacamole users/connections with no live session → removed

Schedule it every 5 minutes with `pg_cron` + `pg_net`:

```sql
select cron.schedule(
  'cleanup-idle-labs',
  '*/5 * * * *',
  $$select net.http_post(
      url := 'https://<project-ref>.supabase.co/functions/v1/cleanup-idle-labs',
      headers := jsonb_build_object('Content-Type','application/json','Authorization','Bearer ' || current_setting('app.service_role_key')),
      body := '{}'::jsonb
  );$$
);
```

Verify: `select * from cron.job_run_details order by start_time desc limit 10;` and check the function logs for `Cleanup completed: N actions taken`.

### Manual emergency cleanup

Admin-authenticated POST to `cleanup-idle-labs`:

| Body | Effect |
| --- | --- |
| `{}` | full auto-cleanup pass |
| `{"action":"stop-vm","vm_id":"…"}` | deallocate one VM |
| `{"action":"delete-vm","vm_id":"…"}` | delete one VM |
| `{"action":"purge-failed"}` | purge failed VM records |
| `{"action":"clear-guacamole"}` | drop all gateway connections |

Students may only send `{"action":"cancel-provisioning","vm_id":"<their own VM>"}`.

Nuclear option for runaway cost: delete every VM in the resource group from the Azure portal, then run `purge-failed`.

## 6. Rollback

1. **Frontend** — republish the previous deployment from Lovable (instant).
2. **Edge functions** — revert the function source and redeploy; functions are stateless.
3. **Database** — never drop columns to roll back. Add a forward migration that restores the previous behaviour. For the lab status change, a rollback migration would relax the check constraint and the student read policy back to the prior value.
4. **Secrets** — rotate rather than restore; update Cloud Providers and re-run the Azure configuration test.

## 7. Verification / smoke test checklist

```bash
npm run verify   # npm ci, lint, typecheck, build, vitest, deno check, deno test
```

Manual pre-go-live checks:

- [ ] Admin can create, edit and archive a lab template.
- [ ] Student sees only `published` labs.
- [ ] Student launches a lab, VM reaches `running`, Guacamole connects.
- [ ] Student cancels a provisioning lab — only their VM is affected, another student's VM is untouched (403).
- [ ] Ending / reminting **Connect** drops the Guacamole connection only — VM stays `running` (disconnect ≠ deallocate). Remint Connect targets the same VM. Soft-expiry / idle cleanup / intentional `stop-vm` are what deallocate. See `docs/CONNECT_SESSION_LIFECYCLE.md`.
- [ ] Idle/expired cleanup deallocates or deletes the expected VMs.
- [ ] Admin pages load: Virtual Machines, Sessions, Session Audit Log, Cost Analytics, AI Status, Cloud Providers.
- [ ] AI assistant degrades gracefully (503 + retry hint) when the key/quota/provider is unavailable.
- [ ] Cloud access template generation works for each enabled provider.
- [ ] A student account gets 403 on admin routes, admin Edge Function actions, and cannot read other users' rows.

## 8. Incident response

### Provisioning failures
`provision-lab` runs an Azure preflight before touching resources and returns the exact Azure code plus the setting to fix. On failure:
1. Open **Cloud Providers → Test Azure subscription configuration** and run the probe.
2. `SubscriptionNotFound` / `InvalidSubscriptionId` → fix `AZURE_SUBSCRIPTION_ID` or grant the SP access.
3. `AuthorizationFailed` → assign Contributor to the service principal.
4. `AADSTS…` / `invalid_client` → re-enter `AZURE_CLIENT_SECRET` (secret *value*).
5. `ResourceGroupNotFound` → create the RG or fix `AZURE_RESOURCE_GROUP`.
6. Quota errors → check **Azure quota** page; East US `standardBSFamily` is capped at 10 cores.

### Runaway Azure cost
1. Cost Analytics → identify the offenders.
2. `stop-vm` / `delete-vm` on the worst VMs, or `clear-guacamole` + full cleanup.
3. Lower the budget cap in Platform Settings (blocks new provisioning immediately).

### Guacamole failures
1. Check the **provider-matched** admin API: AWS labs → `GUACAMOLE_URL`; Azure labs → `GUACAMOLE_AZURE_URL` (falls back to `GUACAMOLE_URL` until Azure Guac is deployed).
2. Run `clear-guacamole` to drop stale connections, then reconnect.
3. If the gateway container is down, restart the Docker stack; sessions reconnect on next launch.
4. **Dual public gateways (Hub map):**
   - **AWS labs** → `https://guac.skillhub365.co.in` (existing EC2 `3.6.228.159`) — do not remove.
   - **Azure labs** → `https://guac-azure.skillhub365.co.in` (Azure Guac VM; Hub supports the map before the VM exists). Until `GUACAMOLE_AZURE_URL` is set, Connect keeps Azure iframes on the AWS public host so tokens stay valid.
5. iframe HTML on `/guacamole/` must be HTTPS. Guacamole also needs a tunnel:
   - Preferred: WebSocket at `/guacamole/websocket-tunnel` with nginx `Upgrade` / `Connection` headers.
   - Fallback: HTTP tunnel at `/guacamole/tunnel` (Guacamole returns 400 without a query string — that is expected for a bare probe).
   - If the UI loads but the session immediately errors/reconnects, verify nginx proxies both tunnel paths to the Guacamole servlet and that guacd can reach the lab VM **private IP:22/3389** on the lab VNet / VPC.
6. Hub `guacamole-proxy` create-session cannot TCP-probe private lab IPs from the edge runtime (reachability-precheck is skipped). SSH readiness is only guaranteed once guacd can open the port — prefer a short settle after the cloud reports the VM running, and fail closed in the Hub UI instead of reminting sessions forever.

### AI outages
1. `/admin/ai-status` shows provider health, 24h latency/failure graph and breaker state.
2. Circuit breaker trips after 5 failures in 120s and blocks for 60s — the UI shows a retry hint.
3. Check quotas (per user/org/global) before assuming a provider outage.
4. Rotate `LOVABLE_API_KEY` if the gateway returns 401/403.
